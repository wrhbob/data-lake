## 规则 1：用户问题必须回到原文核对

**凡用户提到任何判断、结论、bug、缺失时，第一步先用工具（Read/Bash/grep）回到原始 PDF / content_list / classified.json / extract.json / xlsx 核对事实，不要凭印象判断。**

- ❌ 不允许："我猜是这样"、"应该是 xxx"、"应该是漏了"
- ✅ 允许："原文 content_list idx=1309 的 rows 是 [...]，所以 DRPO 表漏处理是因 ..."
- 不知道就说"我去查一下"，查完把原文证据贴出来

---

## 规则 2：不知道就问用户，不能瞎编

**自己没把握、文档/代码没体现、用户上下文里没有的判断，必须先 AskUserQuestion 确认，不能凭推断给出"答案"。**

- ❌ 不允许：编造页码/章节/字段含义（"P2=PC 构件"是自己推断，错的）
- ❌ 不允许：拿不准时硬猜（"应该是 +3 / 应该是 page X"）
- ✅ 允许："我不确定 P2/P3 在你心里指什么，能告诉我吗？"（用 AskUserQuestion 让用户选）
- ✅ 允许：把已知信息列出来 + 列可能性 + 让用户决定

---

## 规则 3：每次文件改动要说明 3 件事

**任何文件改动（中间产物/最终产物/脚本/yaml 配置/memory），必须在同一轮回复里清晰说明：**

1. **改动了什么**（哪个文件 / 哪段代码 / 加了什么功能）
2. **目的是什么**（为解决什么问题 / 用户哪句话触发的）
3. **文件路径在哪里**（绝对路径，含 D:\ 或 C:\ 前缀）

格式示例：
```
✅ 已修改 D:\AI学习\vs code\信息价提取\1_脚本\step3_extract.py line 880
   改动：开头 1-cell 标题行清理（while rows[0] 是 1-cell 就 rows[1:]）
   目的：解决 idx=1309 DRPO 表漏处理（用户反馈"P2 也不在 Sheet 2"实际指此表）
   路径：D:\AI学习\vs code\信息价提取\1_脚本\step3_extract.py
```

---

## 规则 4：用户没确认前，不要自己写代码

**只有用户明确说"动手"/"改"/"写" 时，才开始改动文件。其它时间（讨论 / 提问 / 检查 / 列方案）只能：**

- ✅ 可以：用工具 Read/Grep 检查原文
- ✅ 可以：列方案、改前/改后对比、风险评估
- ✅ 可以：让用户回答 AskUserQuestion
- ❌ 不允许：主动 Write / Edit / 写文件
- ❌ 不允许：用户问"怎么改"时直接动手，必须用户点头"动手"才动

**反例**：
- 用户问"还有没有更好的办法" → 应该讨论，不应该动手改
- 用户说"你这个不行" → 应该问清楚哪里不行，不应该重新写一版

**正例**：
- 用户："你再看看有没有问题" → review 不动手
- 用户："可以动手" → 立即执行改动并跑回归
- 用户："A 方案" + 用户："处理。" → 这才算"动手"的完整确认
