# quota-unified 封存说明

> **状态：已封存（2026-08-14）**。本模块暂停推进，代码保留作参考，不再实装到网站。
> 相关规格：`SPEC.md`（v0.4.3）、`profile_schema.py`、`baseline.py`、`features.py`。

---

## 这个模块原本想干什么

把「每个省各写一个 extractor 脚本」的老路，收敛成「一套 baseline + 省级 Profile 声明」的通用定额提取器，目标是对新省**只加一份 Profile、零新脚本**，并由脚本自动判断特征、自动选择/复用 profile。

三层积木模型：
- `baseline.py` —— 跨省一致的通用逻辑（HTML 网格展开、行分区、单位归一等）
- `profile_schema.py` —— P 类 flag（编码正则、材料表头、章节体系、费用 emit 策略…），共 10 个预置 profile
- `features.py` —— B 类特征检测脚本

## 现状盘点

| 项 | 状态 |
|---|---|
| 预置 profile | 10 个：sc-2018 / cq-2018 / gd-2018 / hu-2018 / bj-2021 / yn-2020 / ha-2016 / sh-2016 / hn-2018 / sz-2023 |
| 后端生产线 | 未接。`quota/parser/quota_parser/pipeline.py` 仍调旧 extractor（5 省：sc/cq/gd/hu/bj） |
| `features.py` 自动检测 | 只检测 4 个特征（bracket_qty / labor_name_keywords / machine_unit_keywords / extra_cost_labels），均为云南/河南手写 |
| 「扫 MD → 自动勾选 → 匹配最像 profile → 复用」闭环 | **不存在** |
| 新旧对拍 | `_parity_check.py` / `_parity_aligned.py` 可做 0 diff 回归 |

## 封存原因（评估结论）

1. **目标没落地**：核心价值「脚本判断特征 + 自动选 profile」这一环完全没实现。现状全靠人工看 + agent 试。
2. **自动检测是难点且有天花板**：检测器只能识别「已写过规则的特征」；新省的全新特征第一次照样识别不了，消灭不了「新特征的第一次判断」。
3. **「小异」分两类，比例决定成败**：
   - 配置差异（regex/label/布局）→ 进 profile flag，零代码 ✅
   - 逻辑差异（emit 顺序、括号量语义、材料费判定、跨页拼接）→ 必须写代码 ❌
   目前逻辑类差异已冒出不少，若比例继续偏向逻辑类，「新省零代码」就落空。
4. **现阶段对比一省一脚本，收益有限**：quota-unified 的真实收益只有「去重 + 单点修 bug + 回归可验证」，而非「新省零代码」。

**定性**：baseline/profile 这层（共享库 + 省级配置）已经赚到了去重和单点修复的价值；但「统一一切 + 自动检测」这层是**提前抽象（premature abstraction）**，暂未兑现，甚至可能永远兑现不了。

## 结论

- **暂不实装到网站**，避免把成本花在「前端配合 + 新旧对拍 + 边界坑」上，而这些成本对「验证 quota-unified 到底有没有用」帮助不大。
- 代码保留作**参考实现**，实际生产继续用旧的一省一脚本。

## 解封条件（满足任一再评估）

1. 实际要覆盖的省份明显超过 5-6 个，且长期持续接新省（去重 + 单点修 bug 的价值随省数放大）。
2. 样本攒到足够多（约 20+ 省），「特征空间有限」的假设得到验证，逻辑类差异不再逐省新增。
3. 明确降级定位为「**共享库 + 显式 profile（人工填）**」，放弃自动检测的执念，只保留去重 + 单点修复。

在达到上述条件前，不建议继续用「统一一切 + 自动检测」的叙事推动本模块。
